## ۱. نمای کلی سیستم

### ۱.۱ تعریف

سامانه کارگزاری یک **پلتفرم B2G سه‌سرویسه** است که واسط بین متقاضیان (اشخاص حقیقی/حقوقی) و سازمان ثبت اسناد و املاک کشور عمل می‌کند:

```
متقاضی ← [سامانه کارگزاری] ← [مرکز تبادل اطلاعات ملی] ← سازمان ثبت
                                  ↑
                    سامانه ثنا / ثبت احوال / شاهکار / مانا
```

### ۱.۲ اصل راهنما: «کارگزار مسئول کیفیت داده است»

از آنجا که مرحله نهایی ثبت در سازمان **کاملاً خودکار و بدون دخالت انسانی** انجام می‌شود، اصل اساسی طراحی این است:

> هر داده‌ای که از سامانه کارگزاری خارج می‌شود، باید **پیش‌اعتبارسنجی شده** باشد — چون فرصت اصلاح دستی در انتهای زنجیره وجود ندارد و بازگشت داده یعنی توقف کل پرونده تا رفع نقص.

### ۱.۳ سه گیت کنترلی کلیدی

| گیت | محل | کنترل‌کننده |
|---|---|---|
| احراز هویت و نمایندگی | ابتدای هر سرویس | کارشناس ثبتی-حقوقی + استعلام سیستمی |
| اعتبارسنجی داده پیش از ارسال | قبل از Submit به سازمان | Rule Engine داخلی کارگزار |
| ثبت نهایی | سمت سازمان | Rule Engine خودکار سازمان (خارج از کنترل ما) |

## ۲. دسته‌بندی زیرساخت‌ها (۱۰ لایه)

### لایه ۱: هویت و احراز (Identity & Verification)

| سرویس | ورودی | خروجی | وابستگی بیرونی |
|---|---|---|---|
| احراز کد ملی + سن + حیات | کد ملی | تایید/رد + نام و مشخصات | شاهکار / ثبت احوال |
| استعلام ثنا | کد ملی | وضعیت ثبت‌نام (فعال/غیرفعال) | سامانه ثنا (قوه قضاییه) |
| استعلام مالکیت شماره موبایل | شماره موبایل + کد ملی | تایید/رد تطابق | شاهکار مخابراتی |
| استعلام سند رسمی نمایندگی | رمز تصدیق + شناسه سند | صحت سند + مشخصات وکیل/نماینده | سامانه اسناد رسمی / کانون سردفتران |
| OTP | شماره موبایل | ارسال + اعتبارسنجی (انقضا: ۲ دقیقه، حداکثر ۳ بار تلاش) | ارائه‌دهنده پیامک |

**ملاحظات طراحی:**
- همه استعلام‌ها باید **Cache** کوتاه‌مدت داشته باشند (مثلاً وضعیت ثنا تا ۱ ساعت) برای کاهش latency و وابستگی به قطعی سرویس‌های بیرونی.
- OTP باید با محدودیت rate-limiting (حداکثر ۵ درخواست در ۱۰ دقیقه به ازای هر شماره) پیاده‌سازی شود.

### لایه ۲: یکپارچه‌سازی با سازمان (Integration)

| جزء | شرح |
|---|---|
| **Gateway** | نقطه ورود/خروج واحد به مرکز تبادل اطلاعات ملی |
| **Circuit Breaker** | محافظت در برابر قطعی یا کندی پاسخ سازمان |
| **Retry Policy** | تلاش مجدد با Backoff تصاعدی (۱ث، ۲ث، ۴ث، ۸ث، ۱۶ث) |
| **Message Queue** | صف ارسال برای درخواست‌های asynchronous (اگر سازمان پشتیبانی کند) |
| **Dead Letter Queue** | درخواست‌های ناموفق پس از اتمام retry — نیاز به مداخله دستی |
| **Sandbox** | محیط تست سازمان برای توسعه — باید از سازمان درخواست شود |

**الگوی طراحی پیشنهادی:** Adapter Pattern — هر سرویس سازمان (نقشه/ادعا/گواهی) یک Adapter مجزا دارد که پشت Gateway مشترک قرار می‌گیرد.

### لایه ۳: نقشه و GIS

| قابلیت | شرح |
|---|---|
| ذخیره‌سازی نقشه | فایل‌های DXF/DWG (AutoCAD) و GeoJSON/Shapefile (WebGIS) |
| اعتبارسنجی Geo-tag | استخراج EXIF/GPS از عکس‌های ارسالی ← تطبیق با مختصات اعلامی ملک (تحمل خطا: شعاع ۵۰ متر) |
| خروجی مانا | تبدیل فرمت داخلی به فرمت موردنیاز سامانه مانا (جزئیات: از سازمان دریافت شود) |
| نمایش نقشه | کتابخانه OpenLayers/Leaflet روی نقشه پایه OSM (یا کاداستر ملی در صورت دسترسی) |
| عکس‌های میدانی | ذخیره ۴ عکس از ۴ ضلع + metadata (زمان، موقعیت، شناسه کارشناس) |

**نکته مهم:** اپلیکیشن موبایل کارشناس نقشه‌بردار باید قابلیت عکس‌برداری با درج خودکار Geo-tag و زمان را داشته باشد (دستکاری metadata در سمت سرور تشخیص داده شود).

### لایه ۴: ذخیره‌سازی داده

| جزء | نوع | شرح |
|---|---|---|
| **Primary DB** | RDBMS (PostgreSQL) | وضعیت پرونده‌ها، workflow state، اطلاعات متقاضی، کدهای رهگیری |
| **File Storage** | Object Storage (S3-compatible) | اسناد هویتی، تصاویر گواهی، عکس‌های ملک، فایل‌های نقشه |
| **Audit Log** | Append-only store (Elasticsearch / separate PG schema) | تمام رویدادها: تغییر state، دسترسی کاربران، ارسال/دریافت به سازمان |
| **Cache** | Redis | Session، OTP، استعلام‌های موقت (ثنا، ثبت احوال) |

**قاعده دسترسی به فایل‌ها:** هر فایل با Pre-signed URL با انقضای کوتاه (۵ دقیقه) ارائه شود — دسترسی مستقیم به Object Storage ممنوع.

### لایه ۵: مدیریت نقش‌های داخلی

| پنل | کاربر | شرح |
|---|---|---|
| **مدیریت کارشناسان** | ادمین کارگزاری | ثبت/ویرایش/غیرفعال‌سازی کارشناس، تخصیص به پرونده |
| **پنل کارشناس ثبتی-حقوقی** | کارشناس حقوقی | بررسی اسناد، احراز نمایندگی، تایید/رد |
| **پنل کارشناس نقشه‌بردار** | کارشناس نقشه‌بردار | دریافت مأموریت، آپلود عکس و نقشه، تکمیل جدول توصیفی |
| **اپ موبایل نقشه‌بردار** | کارشناس نقشه‌بردار | عکس‌برداری Geo-tagged میدانی، مشاهده مختصات ملک روی نقشه |

### لایه ۶: پرداخت

| جزء | شرح |
|---|---|
| درگاه بانکی | اتصال به PSP (پرداخت‌یار) برای پرداخت آنلاین |
| کیف پول | ثبت علی‌الحساب، محاسبه مابه‌التفاوت نهایی |
| استرداد | برگشت وجه خودکار در صورت رد درخواست (به‌جز هزینه بررسی اسناد) |
| مدیریت تعرفه | پنل ادمین برای به‌روزرسانی سقف تعرفه‌های اعلامی سازمان |

### لایه ۷: اطلاع‌رسانی

| کانال | کاربرد |
|---|---|
| **پیامک** | OTP، هشدار قانونی (ادعای واهی)، اعلام کد رهگیری، اعلام تغییر وضعیت |
| **نوتیفیکیشن درون‌برنامه‌ای** | اعلان‌های غیرفوری: تخصیص کارشناس، آماده بودن نتیجه |
| **ایمیل** (اختیاری) | گزارش‌های دوره‌ای، رسید پرداخت |

### لایه ۸: راهنمایی هوشمند (AI)

| جزء | شرح |
|---|---|
| **ورودی** | نوع ادعا، مستندات، وضعیت ثبتی ملک |
| **موتور** | RAG روی قوانین و رویه‌های ثبتی + Rule-based fallback برای موارد قطعی |
| **خروجی** | پیشنهاد نوع اقدام قانونی + ارجاع به مواد قانونی مرتبط |
| **مرزبندی** | **صرفاً راهنمایی** — هر خروجی با disclaimer «این نظر رسمی حقوقی نیست» همراه باشد |
| **گزارش** | ثبت لاگ مشاوره + گزینه «ارجاع به کارشناس انسانی» |

### لایه ۹: امنیت و انطباق

| حوزه | راهکار |
|---|---|
| **رمزنگاری در حالت سکون** | AES-256 — پایگاه داده + فایل‌ها (کد ملی، اسناد هویتی) |
| **رمزنگاری در انتقال** | TLS 1.3 — تمام ارتباطات داخلی و خارجی |
| **RBAC** | نقش‌ها: متقاضی، کارشناس حقوقی، کارشناس نقشه‌بردار، ادمین، حسابرس (read-only) |
| **Audit Log** | Immutable + append-only + قابل export برای سازمان |
| **OWASP Top 10** | آمادگی برای تست نفوذ: SQL Injection، XSS، CSRF، SSRF، IDOR |
| **Rate Limiting** | API Gateway: محدودیت نرخ به ازای IP و کاربر |
| **WAF** | Web Application Firewall در لبه شبکه |
| **Secrets Management** | Vault / KMS برای کلیدهای API سازمان و توکن‌های دسترسی |

### لایه ۱۰: زیرساخت عملیاتی

| جزء | شرح |
|---|---|
| **محیط‌ها** | Dev ← Staging ← Production (ایزوله کامل) |
| **Containerization** | Docker + Kubernetes برای مقیاس‌پذیری افقی |
| **Monitoring** | Prometheus + Grafana: نرخ خطای API سازمان، latency، وضعیت صف‌ها |
| **Alerting** | هشدار در صورت: قطعی اتصال به سازمان > ۲ دقیقه،堆积 صف > ۵۰، خطای ۵xx > آستانه |
| **Backup** | روزانه کامل + WAL archiving برای Point-in-time recovery |
| **DR** | Replication跨 دیتاسنتر (با توجه به الزام حاکمیتی: داخل کشور) |

```
                      ▼
              ┌───────────────────┐
              │ CLAIM_IN_PROGRESS │
              └────────┬──────────┘
                       │ کد رهگیری ادعا صادر شد → deadline_2years = now + 2y
                       ▼
              ┌────────────────────┐
              │  CLAIM_COMPLETED   │
              └────────┬───────────┘
                       │ شروع سرویس گواهی اقدام
                       ▼
              ┌───────────────────┐
              │ CERT_IN_PROGRESS  │ ←── deadline_5months (در صورت فوت متقاضی)
              └────────┬──────────┘
                       │ کد رهگیری گواهی صادر شد
                       ▼
              ┌──────────────────┐
              │  CERT_COMPLETED  │  ←── زنجیره کامل شد
              └──────────────────┘
```

### ۵.۲ ماشین زمان (Scheduler)

| Job | Trigger | Action |
|---|---|---|
| `check_deadline_2years` | روزانه، ۰۰:۰۰ | پرونده‌های `CLAIM_COMPLETED` که `now > deadline_2years` → `EXPIRED` + پیامک به متقاضی |
| `check_deadline_5months` | روزانه، ۰۰:۰۰ | پرونده‌های با فوت متقاضی که `now > deadline_5months` → `EXPIRED` + پیامک به وراث |
| `check_expired_otp` | هر ۱ دقیقه | OTPهای منقضی‌شده → invalidate |
| `retry_failed_integration` | هر ۵ دقیقه | درخواست‌های failed در صف → retry با backoff |

## ۶. راهبرد امنیتی

### ۶.۱ مدل تهدید (Threat Model — STRIDE)

| تهدید | سناریو | راهکار |
|---|---|---|
| **Spoofing** | جعل هویت متقاضی با کد ملی دیگران | OTP به شماره ثبت‌شده در شاهکار + استعلام تطابق کد ملی-موبایل |
| **Tampering** | دستکاری مختصات نقشه / عکس‌های میدانی | اعتبارسنجی EXIF + checksum فایل‌ها + Audit Log تغییرات |
| **Repudiation** | انکار ارسال داده یا دریافت نتیجه | Immutable Audit Log + رسید دیجیتال هر تراکنش با سازمان |
| **Information Disclosure** | لو رفتن اسناد هویتی/مالکیتی | Encryption at rest + Pre-signed URL + حذف خودکار فایل‌های موقت |
| **Denial of Service** | حمله به API Gateway | Rate Limiting + WAF + Auto-scaling |
| **Elevation of Privilege** | دسترسی غیرمجاز کارشناس به پرونده | RBAC + Row-Level Security در دیتابیس |

### ۶.۲ الزامات تست نفوذ

| مورد | شرح |
|---|---|
| OWASP ASVS Level 2 | حداقل سطح امنیتی هدف |
| API Security | احراز هویت JWT با RS256، انقضای کوتاه Access Token (۱۵ دقیقه)، Refresh Token rotation |
| Data Isolation | هر کارگزاری فقط به داده پرونده‌های خود دسترسی دارد (Multi-tenancy در صورت وجود چند کارگزار) |
| Dependency Scanning | اسکن خودکار وابستگی‌ها (CI/CD pipeline) |
| SAST/DAST | تحلیل ایستا و پویا پیش از هر release |
